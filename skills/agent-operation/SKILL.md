# 操作长期执行 agent

来源：2026-07-16 一次完整实战——操作 codex 完成其配置文档镜像工程（S0-S7，跨约 24 小时，含 5 类故障处置），操作逻辑复刻自"用户操作 Claude"的真实模式。

## 核心心智

**操作者只做四件事：派、验、裁、推。** 执行永远在 agent 手里；操作者的一切决策质量取决于被操作者暴露了什么——所以本 skill 的大半条款都在解决"如何让 agent 暴露真实状态"和"如何不被虚假信号骗"。

第二条心智：**状态判断只信现场结果，不信心跳信号。** 通知、空闲信号、"我做完了"的口头汇报都可能失真；文件在不在、commit 有没有、命令退出码是多少不会说谎。

## 管线设计

- **递进式，不打包**：把工程拆成"盘点→定方案→执行（可再分批）→审查→异源终审→收口→复盘"式的步骤链，一步一验一推。禁止把多步塞进一次派单——后一步的内容取决于前一步的验收结果
- **每步派单即建任务、标 in_progress，验收即 completed**——清单必须实时反映真实进度
- **执行大步骤要分批**（如"移植 50 个文件"拆成 3 批）：防 agent 上下文爆掉，也让故障半径可控
- **开工前先 git 化**：受操作对象若是文件体系，第一步就快照进 git——此后每一刀都有历史，备份文件退化为可选

## 派单纪律（叠加在 dispatch-briefing 模板之上的长任务条款）

- **汇报义务写死在 prompt 里**：完成即主动汇报；遇阻也要汇报卡点，禁止静默空转；长任务每过一个里程碑发一行进度
- **交付落盘化**：报告/产物必须"写成文件 + commit + push"，不许只发消息——文件存在与否可一档核查，天然进审计轨，且不依赖消息通道可靠性。通道断了、会话丢了，任何新 agent 都能靠落盘报告接手
- **断点条款**：预告 agent "若遇平台故障（模型容量/超时），先把已完成部分 commit 再退出"——重启即增量续做
- **上下文纪律**：明确告诉 agent 它上下文有限，读写要"一次一个对象、处理完放下"；大批量机械操作用 rsync/脚本，不逐文件装载

## 通知处理与状态判定

- **实质消息是唯一真信号**：只处理带内容的汇报/求助。无内容状态或 idle 通知只表示"该 agent 一轮结束"，不携带进度信息——一律零成本忽略，禁止为裸 idle 产生查询、催报或长回复
- **新 spawn 首个 idle 做一次现场核查**：专防"spawn 后不执行 prompt 直接装闲"，发现未开工立即重发指令唤醒
- **无报告三态判定**：先查现场（文件/commit/进程/退出码）分辨——①干了没报→自行验收；②正在干→不打扰；③没干→重发唤醒
- **催报上限 1 次**：催后只看现场变化；再无响应且现场无进展→换通道或重建 agent（交付落盘化保证了重建零损失）
- **无人值守窗口配定时检查点（自推进循环）**：预计跨小时/过夜的工程，挂周期唤醒（Codex App 用 automation 能力；**10 分钟一拍**为默认——用户 2026-07-22 修订，30 分钟太久）。教训：曾因验收后被动等报告而空转一夜。循环配方：
  - **唤醒 prompt 自携带全部循环逻辑**（下一拍的自己没有本拍记忆之外的上下文）：①查现场的具体命令 ②三态处置规则 ③当前管线（下一步是什么）④记日志 ⑤"未收口→再挂一拍传本 prompt；收口→停止循环向用户交账"
  - **与事件通知的分工**：harness 能自动通知的（后台任务完成）靠通知即时响应，定时器只是兜底心跳——别用短周期轮询替代事件驱动
  - **退出条件写死在 prompt 里**：以"管线终点完成"为唯一停表条件，防止循环永续或提前失守

## 验收工具箱（不通读全文也能验收）

按成本从低到高使用：

1. **一档核查**（存在性/结果性）：目录、文件、行数、commit hash、push 状态、退出码、grep 计数。安全门（密钥扫描、禁入文件检查）也属此档——泄密不可逆，永远值得跑
2. **报告自带证据**：派单时要求报告含"原文→新文、文件:行号、前后行数、自查 grep 结果"——证据不全的报告退回
3. **会话事实核报告**：拿操作者自己记得的裁决现场对照报告里的"依据"字段——引据张冠李戴（结论对、理由错）是高发缺陷，且会向下传染到后续施工
4. **关键问句**：审"适配/移植"类工作必问"这个删除是'载体无对应物'还是'教义本身'？"——镜像移植最大的陷阱是把教义误判为载体而删掉
5. **委派验证**：全文级审查不必操作者亲自读——让 Codex 原生 agent 互审或派独立 code-review；只有用户在当前任务明确授权外部引擎时，才通过对应桥接能力做异源终审（Claude 使用 `claude-delegate`）

## 裁决

- **分层放权**：常规判断 agent 自己拍；关键逻辑（授权边界/判定阈值/用户拍板过的决定）要求 agent 只上报不动手，操作者逐条裁决后回发
- **裁决基准 = 已定稿教义**：用户放权后，操作者以既有拍板为准绳裁决，不重开已决议题；无先例的新分叉按"无风险且符合推进方向"选，交付时注明
- **敢于收紧**：agent 的建议多数照批，但涉持久写入/供应链/对外动作的要主动收紧（如"自动 pip install"改为"报告确认后才装"）
- **纠错要纠到依据**：发现引据错误时，除改结论文档外责令更正依据字段——错误依据留在施工文档里会污染后续判断

## 故障档案与对策

| 故障 | 症状 | 对策 |
|------|------|------|
| 静默空转 | spawn 后即 idle、零动作零汇报 | 首 idle 现场核查 → 重发指令唤醒 |
| 干完不报 | 现场有产出、消息通道无报告 | 按三态①自行验收，不再催 |
| 通道休眠 | 跨长窗口零会话零 commit | 换通道（`send_message` 无响应时用 `followup_task` 唤醒，必要时中断并重建 agent），靠落盘报告传上下文 |
| 模型容量瞬断 | "model at capacity" 中断 | 核实中断点是否留残局 → 原单重发 + 断点条款 |
| resume 目标漂移 | multi-agent 扇出后 `resume --last` 落到子会话、拒绝输入 | 弃考古，开新会话 + 落盘报告接手；需要真连续性时提前记录根会话 ID |

## 操作日志（复盘的原料）

开工即建一份操作日志（scratchpad 即可）：派单/事件流水表 + 统计计数器（派单数/报告数/催报数/现场核查数/纠错数/裁决数/返工数）+ 随事件追加的复盘素材。每次处置顺手记一行——收口时的复盘报告就是把它整理成文，不靠回忆。
